# Name the Run pipeline hand-offs with typed stage results

The four stage modules (ADR-0001) exchange string-keyed `dict[str, Any]`, so each stage's output contract lives in four places: the return literal, a docstring, the orchestrator's subscript expressions, and test key-assertions. That contract has already drifted silently — `setup`'s docstring omits the `open_` key it returns, and two returned keys (`resolved_component_params`, `locked`) are read by no production code at all — and the newly adopted mypy is blind at exactly these seams. Each producing stage now returns a frozen dataclass it owns: `SetupResult` in `pipeline/setup.py`, `ExecutionResult` in `pipeline/execution.py`, `PublishingResult` in `pipeline/publishing.py`, with fields carrying their real types (`OptimizationSource`, `RunSplitsResult`, `pd.DataFrame`). Completion keeps returning the CLI-facing result dict: that return is a terminal contract surface (`cli_commands/run.py` consumes it via `.get()` and serialises it to JSON), and house precedent types the internal spine while terminal artifacts stay dicts. The stage seams stay exactly where ADR-0001 put them, and ADR-0004's deferral of typed Evidence *payloads* stays deferred — stage results are a different surface.

The field-admission rule is **thread identities, recompute values**. `SetupResult` stores five fields: `store_path` (an identity — every stage must agree on the same store, and threading makes agreement true by construction), `optimization_source` and `split_result` (genuine products, born from Lock resolution and source construction), and `close`/`open_` (products of setup's data preparation — downstream stages never hold the data bundle, so these are not derivable from inputs they have). `strategy_evidence` is a derived `@property` over `optimization_source`, so divergence is unrepresentable and the `evidence["strategy"]` key knowledge stays inside the setup module. The config builtins (`to_builtin(config.optimization)`, `to_builtin(config.portfolio)`) and `store_namespace` (zero-arg, deterministic) are values — deterministically derivable from inputs every consumer already holds — so consumers recompute them. Only the call repeats; the knowledge, how canonicalization works, stays in exactly one module (ADR-0003). This also deletes the orchestrator's duplicate `candidate_store_namespace()` computation.

Consumption follows a majority/aggregator line: a stage takes a result whole when it reads most of it or is the designated aggregator, and takes explicit fields otherwise. Execution takes `SetupResult` whole (reads 4 of 5 fields). Publishing reads 2 of 5, so it takes `optimization_source` and `store_path` explicitly, plus `ExecutionResult`. Completion is the aggregator — it takes `SetupResult` and `PublishingResult` whole, collapsing its 14 kwargs to 8 — and the orchestrator reads as a pure four-call sequence.

Landing is two mechanical steps, each with the same oracle. Step 1 names the hand-offs: result types with today's eight consumed fields, the two dead keys deleted, zero computation moved; `tests/support` gains a `make_setup_result` factory and `run_pipeline_completion` gets its first direct unit test. Step 2 slims to the five-field end state: builtins and namespace recomputed at use sites, the `strategy_evidence` property added. The oracle for both: `manifest.json` and the strategy artifact are byte-identical (which holds through step 2 because `to_builtin` is deterministic).

## Considered options

- **Strict naming** (ship `SetupResult` with all eight consumed fields as the end state, move no computation): rejected — a typed interface about to be minted should not enshrine accidents. The builtins ride along today only because a dict makes adding keys free; the moment the hand-off gets a name, every field becomes documented contract, and removing one later is a second interface change with its own justification burden. Curating the fields *is* the naming work. Strict naming survives only as step 1 of the landing, never as the destination.
- **Bare `OptimizationResult` return from execution** (no one-field wrapper): the deletion-test-minimal shape, since execution produces exactly one already-typed value. Rejected for uniform stage returns — every stage hands off a result type named after the stage; the one-field `ExecutionResult` is the accepted cost, and if execution ever grows a second output the wrapper is already there.
- **A `CompletionResult` type**: rejected — completion's return *is* the CLI contract, not an internal hand-off; typing it would type a terminal artifact against house precedent (ADR-0003/0005).
- **Pass-whole everywhere / unpack everywhere**: rejected on both ends. Pass-whole everywhere gives publishing formal dependence on two DataFrames and a split result it never reads — its honest 2-of-5 interface is exactly what ISP protects. Unpack everywhere is the status quo with types: completion keeps ~12 kwargs and the aggregator never gets named as one.
- **A `RunContext` parameter object** (bundling `config`, `recorder`, `data_result`, `array_contract`, `metric_registry`, `run_evidence`): rejected. Handing every stage a context carrying the recorder grants ambient artifact-write authority to stages that deliberately lack it — which stages touch provenance would no longer be readable from signatures. ADR-0004 went out of its way to close exactly this boundary: the ledger takes a narrow `persist: Callable[[], None]` hook precisely so optimization gains no dependency on provenance; a `RunContext` carrying the recorder would quietly re-open it. The ambient threading it would "tidy" is in fact already ISP-curated — execution receives `metric_registry` because it computes Metrics, while setup, publishing, and completion receive only `metric_registry_fingerprint` because they embed an identity fact; a context flattens that distinction so every stage gets the whole registry because one stage needs it. The revisit trigger is structural, not numeric: a stage receiving an ambient param it does not use — a dishonest signature — reopens the question; parameter count is a smell only. Any future bundle must be named after a concept, never after a lifetime: the co-traveling trio `data_result` + `array_contract` + `metric_registry_fingerprint` are all facts about what data this Run ran on (adjacent to what `run_data_contract.py` assembles), and a bundle of them must carry that name. A bundle with a domain name is just a module; a bundle named "context" is the thing rejected here. Recording the trigger follows the house protocol for deferred designs: ADR-0001 deferred the evidence accumulator with a revisit note, and ADR-0004 cashed it in when the friction became real.

## Consequences

- Stage output contracts move from prose and subscripts into signatures; mypy checks all four seams. The orchestrator's `metric_registry: Any` tightens to `FrozenMetricRegistry` in the same change.
- `manifest.json` and the strategy artifact are byte-identical through both landing steps — the regression oracle for the whole change.
- Setup's dead keys are deleted; the locked-setup test observes Lock application through `optimization_source.evidence` (`param_mode == "locked"`) instead of reading a relayed copy.
- Publishing and completion gain direct `to_builtin` calls: "who serialises the config snapshot" moves from setup to the consumers that embed it, so the serialisation decision lives with the Evidence rows and artifact payloads that need it.
- Test surface: key-presence assertions become obsolete (the constructor is the contract); `tests/support` gains `make_setup_result`; `run_pipeline_completion` gets its first direct unit test; duck-typed fakes survive unchanged because tests sit outside mypy's `files = ["research"]`.
- Amends nothing: ADR-0001's stage seams are untouched, and ADR-0004's deferred typed Evidence payloads stay deferred.
- **Amended by [ADR-0024](0024-run-arrays-one-constructor-for-both-views.md)**: `SetupResult`'s field enumeration is now four — the `close`/`open_` frames (which had further drifted to include `pnl_close`/`pnl_open`) are replaced by the single `arrays: RunArrays` product of the market-data preparation constructor. The field-admission rule and the stage seams are unchanged.
- **Amended by [ADR-0025](0025-run-data-facts-one-value-behind-the-data-projections.md)**: the revisit trigger is discharged — the co-traveling trio `data_result` + `array_contract` + `metric_registry_fingerprint` becomes the domain-named `RunDataFacts` value in `run_data_contract.py`, carrying its projections as methods. The recorder stays outside that seam; no stage gains ambient authority.
