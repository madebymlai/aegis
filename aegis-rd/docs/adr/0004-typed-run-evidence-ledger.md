# Give the Run a typed Evidence ledger

`run_pipeline`'s four stages (ADR-0001) glue together by threading and mutating one untyped `optimization_evidence: dict[str, Any]`: `setup` births it, `execution` and `publishing` mutate it, `completion` reads it. Its shape lives nowhere, `recorder.persist()` fires from inside two `execution` failure branches, and persist-on-failure is inconsistent — `execution` saves partial **Evidence** on failure but `publishing` does not (if `publish_candidates` raises, the `manifest.evidence["optimization"]` assignment never runs and the partial evidence is lost). ADR-0001 explicitly deferred an "evidence accumulator" as premature, noting it "can be revisited later without changing module boundaries." This is that revisit; the stage boundaries stay exactly where ADR-0001 put them.

We introduce a deep module `optimization/evidence_ledger.py` exposing a `RunEvidence` ledger with a tiny interface — `record(section, payload)`, `fail(stage, err)`, `snapshot()`. It owns the whole `manifest.evidence` shape: the run-level seeds (`component_registry_fingerprint`, `data_arrays`) and the schema-versioned `optimization` section (`optimization_route.v1`) with its incrementally-appended sub-sections (`preflight`, `execution`, `candidates`, `locks`, …). Stages keep their seams but stop returning and mutating a raw dict — they receive the ledger and append typed sections through it.

The ledger is the **sole writer** of `manifest.evidence`: one canonical store, one writer, one persist path. `record()` mutates the single live evidence dict directly; the recorder serializes that same dict, so the Manifest is never stale and there is no second representation to desync. The ledger takes a narrow `persist: Callable[[], None]` hook rather than importing `RunRecorder`, so `optimization` gains no dependency on `provenance`. `fail(stage, err)` records a typed failure section and persists, making persist-on-failure uniform across all stages and closing the `publishing` gap. `candidate_count`, formerly computed in `publishing`, is derived inside the ledger when the `candidates` section is recorded.

## Considered options

- **Optimization-section ledger** (own only `manifest.evidence["optimization"]`): smaller, but leaves the run-level seeds written by a raw `recorder.manifest.evidence = {...}` literal in the orchestrator — evidence assembly still has two homes. Rejected in favour of a Run-level ledger so there is exactly one.
- **Pure accumulator** (orchestrator reads `snapshot()`, then assigns it and calls persist): keeps the ledger free of any persist concern, but relocates the scattered persist-on-failure logic up to the orchestrator instead of eliminating it — the candidate's stated win, "persist-on-failure in one place," is not delivered. Rejected.
- **Flush-on-persist** (ledger holds a private dict and writes `snapshot()` into the Manifest on persist): encapsulates behind a façade, but creates two evidence representations that desync whenever the recorder persists for an unrelated reason (a stage mark, a status transition) — two paths to the same bytes. Rejected in favour of a single canonical store the ledger writes directly.
- **Typed payloads per section** (a dataclass for each `preflight`/`execution`/`candidates`/`locks`): fuller No Primitive Obsession, but the payload producers (`build_preflight`, `result_evidence`, `candidate_rows_from_result`) are owned by other modules and other deepening candidates (a typed `CandidateRow`; collapsing the two Metric-computation surfaces). Typing them here would swallow those changes into this one. Deferred — additive on top of this ledger; this candidate types the section *keys* (a `Section` enum), not the payloads.
- **Redaction/truncation in `fail()`** (unify the three `{error_type, message}` failure dicts and always redact): the known-secret redaction guards a path no committed Run travels — zero configs use `{env: ...}` secret refs; sources are `yf` (no credential) and one `ibkr`. Building the invariant now is YAGNI; redaction stays at the existing `run_pipeline` boundary and becomes uniform additively if a credentialed source ever ships.

## Consequences

- New module `optimization/evidence_ledger.py` (class `RunEvidence`); `run_pipeline` and the four `pipeline/*` stages take the ledger instead of threading `optimization_evidence`. Each stage's return dict shrinks by one key.
- The persisted `manifest.json` is **byte-identical** before and after — the `optimization_route.v1` nesting and every section key are preserved — so "Manifest unchanged" is the regression oracle. Section *ordering* is not a ledger concern: `canonical_json_bytes` sorts keys, so insertion order is invisible in both the file and the content hash.
- Persist-on-failure becomes uniform: every stage failure records a typed failure section and persists the accumulated evidence, closing the `publishing`-stage gap where partial evidence was previously lost.
- No dependency on the canonical-serialization work (ADR-0003): the ledger appends builtins, and serialization stays in the Manifest layer. The two are hash-orthogonal and can land in either order.
- Amends ADR-0001: its deferred "evidence accumulator" is now the `RunEvidence` ledger. Module boundaries are unchanged — the four stage seams stay exactly where ADR-0001 placed them.

**Amendment (2026-07-23).** `RunEvidence.fail(stage, err)` now retains the failure stage only in
memory and persists the Evidence accumulated so far; it no longer writes a second diagnostic into
optimization Evidence. The recorder writes the one terminal failure fact under the Manifest's Run
lifecycle, with stage, exception type, and bounded message. This keeps partial Evidence durable
without allowing Evidence and lifecycle diagnostics to disagree.
