1 · Give the Run a typed Evidence ledger

Strong in-process

research/aegis_research/optimization/pipeline/{setup,execution,publishing,completion}.py · run_pipeline.py

Before — shallow stages, one shared mutable dict

setup → returns 10-key dict
execution → mutates optimization_evidence
publishing → mutates same dict
completion → reads same dict
optimization_evidence: dict[str, Any]
untyped · no schema · threaded + mutated across 4 stages · ordering implicit · recorder.persist() hidden inside stage calls

After — stages stay split, ledger owns the shape

RunEvidence ledger (deep)

one interface: record(section, payload) · fail(stage, err) · snapshot()

setup
execution
publishing
completion

stages append typed sections through the ledger; persist-on-failure lives in one place

Problem. ADR-0001 split the orchestrator into four stages, but they glue together by mutating one untyped optimization_evidence dict — its shape lives nowhere, its ordering is implicit, and recorder.persist() fires hidden inside stage calls.

Solution. Introduce the Evidence ledger ADR-0001 deferred: a deep module owning the dict shape, section keys, ordering, and persist-on-failure. Stages keep their seams but append typed sections instead of mutating a raw dict.

  • locality: Evidence shape lives in one module
  • interface shrinks: stages stop returning 10-key dicts
  • persist-on-failure stops scattering across stages
  • leverage: section keys typed, not stringly-keyed
Complements ADR-0001 — does not reopen it. The ADR explicitly deferred the "evidence accumulator" as premature: "this can be revisited later without changing module boundaries." This candidate is that revisit. Stage boundaries stay exactly where the ADR put them.

Problem. The rule for turning values into reproducible hashed bytes is duplicated six ways with diverging flags — and a Run's product is reproducible, hashed Evidence. The serialization rule is load-bearing but lives nowhere.

Solution. One module owns to_builtin, canonical_json_bytes, and stable-ID hashing (the duplicated sha256[:32] for lock_/cand_). Everyone calls it.

  • locality: one canonicalization rule, one place
  • fixes the allow_nan inconsistency at the source
  • protects the reproducible-Evidence promise
  • delete two to_builtin + four inline dumps

Problem. The same six registered Metrics are computed two ways — accessors for ranking, pf.stats() for reports — so the number a Candidate is ranked on can drift from the number reported for it (e.g. max_dd, total_return scaling).

Solution. A single deep Metric module computes each registered Metric from a portfolio; the ranking path and the report path both consume it. Rendering and Evidence packing stay in reports; computation leaves it.

  • ranked value and reported value agree by construction
  • kill the ~90% duplication in reports.py
  • delete unused MetricTargetAdapter + empty custom/ hook
  • reports keeps only Evidence assembly + render
Sharpens the prior review. 2026-05-27 proposed "deepen reports into Metric computation + Evidence assembly." That didn't land — and walking it now shows the deeper issue isn't inside reports: it's that a second computation already lives in accessors.py. The two must converge, not just split.

Problem. insert_completed_run(candidate_rows: Sequence[Mapping[str,Any]]) forces callers to hand-build dicts shaped like SQL columns. The table schema leaks across the seam; a new column ripples through the builder and the store. Primitive obsession — a Candidate row is not a bare dict.

Solution. A typed CandidateRow / LockRecord at the seam; the store owns the dict↔column mapping internally. Callers construct a domain type, not a SQL-shaped dict.

  • schema stops leaking across the seam
  • locality: column changes stay in the store
  • builder + store share one type, not a key convention
  • the seam becomes a test surface

One module decides validity; no sweep can silently skip the mask.

Problem. Whether a Candidate is full-history-invalid is decided in runner.py, masked in the precompute window callback, and re-counted as "degenerate" in ranking.py — no locality. The asymmetry shows: the selection sweep masks invalid candidates (line 113), the held-out sweep does not (line 387).

Solution. A CandidateValidity module owns invalidity + masking; both the selection and held-out sweeps consume the same interface, so neither can skip it.

  • locality: validity decided in one place
  • closes the held-out masking asymmetry
  • "invalid" vs "degenerate" stop conflating
  • the masking rule becomes a test surface
Note. Whether the held-out asymmetry is user-visible depends on whether an invalid Candidate can become a representative (best/median/worst) — it is masked to NaN on selection, so usually it cannot. The point here is the locality gap that let the two sweeps drift, not a confirmed live defect.

Top recommendation

3 · One canonical serialization + hashing module jump ↑

Smallest blast radius, highest leverage, and it guards the system's core promise: a Run produces reproducible, hashed Evidence. The canonicalization rule is duplicated six ways today with a real inconsistency — the Manifest path omits the allow_nan=False that every hash path enforces. Collapsing it into one deep module behind a tiny interface fixes that at the source and gives every other candidate (Evidence ledger, CandidateStore rows) a single seam to write through. Do this first; it de-risks the rest.

Then: 1 · Evidence ledger (central, fulfills ADR-0001's deferral) and 2 · market-data adapters (largest single module, three adapters already waiting).
